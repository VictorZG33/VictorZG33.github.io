# wentaoz.com

Personal homepage of Wentao Zhang, served by GitHub Pages at https://wentaoz.com.

There is no build step: every file is served as-is. Edit and push to `main`; GitHub Pages redeploys in about a minute.

- `index.html` is the homepage. The film strip's thickness and material live in the address (`?d=70&m=al2o3`), so a link opens on the same colour. The growth per ALD cycle behind the cycle count is the `gpc` of each entry in `MATERIALS`.
- `wine-moon/index.html` is 醉月历 Wine Moon, the biodynamic wine calendar.
- `wine-moon/engine.js` computes the Moon's position and the fruit, flower, leaf and root periods. Both the calendar and the Wine Moon card on the homepage load it, so a fix there reaches both.
- `beer/index.html` is 原麦汁 Original Gravity, a field guide to beer at `/beer/`, in Chinese and English, linked from the homepage's Wine tab. It has 28 styles, each with its BJCP 2021 numbers, how it is brewed (the grain, the mash, the boil, the fermentation and the conditioning) and a drawing of it in its glass, and 50 hops with their acids, oils and aromas, among them New Zealand's and Australia's new varieties and a few growers' experimental ones (Eggers Hops' pESH and Eggers Special, HPA's numbered trial lines). A section on sugar and sweetness has a calculator, which takes the original gravity and either the final gravity or the alcohol (a Chinese label's 原麦汁浓度 and 酒精度 will do) and works out the real extract, the attenuation and the calories by Balling's formulas, and answers two questions: why a double dry-hopped IPA tastes sweet, and whether our own amylases turn its dextrins into sugar. The style and hop being shown are kept in the address (`#s=hazy-ipa&h=citra`), a question by its id (`#q-ddh`), and the language in `localStorage` under `gravity.lang`.
- `beer/data.js` holds the styles, the hops and the questions, every text in both languages. The style numbers are the BJCP's; `node beer/check.mjs` compares them with the BJCP's own data (it reads the BeerJSON copy on GitHub) and checks that every hop or question a style names is listed. The hop numbers are the ranges their breeders publish, or failing that the growers and merchants of the hop's home country, with the sources listed under each hop. The homepage card says how many styles and hops there are, so adding one means changing its count there too.
- `beer/colour.js` turns an SRM into the colour of daylight after a given thickness of beer: A. J. deLange's average absorption spectrum of beer, the Beer–Lambert law, then the same CIE and sRGB steps as the homepage film strip. The page draws each glass pixel by pixel with it, each pixel the colour of the beer the light crosses there, and the homepage card's left edge is a gradient taken from it, 2 to 40 SRM through 5 cm. Like `golf/swing.js` it has no DOM, so node can run it.
- `split/index.html` is 两清 All Square, the bill splitter: names first, then each expense with who paid and who shares it, then the settlement with the fewest transfers. The ledger is kept in the browser's `localStorage` under `allsquare.ledger`, and shared ledgers sync through the server below.
- `workers/split` is that sync server, a Cloudflare Worker; see [Shared ledgers in All Square](#shared-ledgers-in-all-square).
- `golf/index.html` is 挥杆镜 Swing Mirror, the golf swing analyser at `/golf/`. A visitor picks a video of one swing; MediaPipe's pose model (loaded from jsDelivr, the model file from Google's storage) tracks 33 body points in every frame, in the browser, and the video never leaves the device. `golf/swing.js` finds address, top, impact and finish in those points and measures tempo, head and hip movement and body angles, with the thresholds for good, watch and fix written next to each measurement. It has no DOM, so it can be run in node against saved landmarks.
- `golf/coach.js` is the optional AI coach: it turns the four key frames and the measurements into one Claude request. By default the page sends it to `workers/golf-coach/`, a Cloudflare Worker at `COACH_ENDPOINT` in `golf/index.html` that calls Claude on the site's own key, kept there as a secret. `.github/workflows/golf-coach.yml` deploys it from the repository secret `ANTHROPIC_API_KEY`; the Worker's README explains the setup. A visitor can tick *Use my own Anthropic API key* instead: the page then calls Claude directly with the key they paste (kept in `localStorage` under `golf.apiKey` only if they tick *Remember*), and a visitor with a saved key starts on it. With `COACH_ENDPOINT` empty, the visitor's own key is the only way.
- `werewolf/index.html` is 盘狼 Table Read, a reasoning aid for werewolf (狼人杀) at `/werewolf/`, in Chinese. You set the player count and the board (villagers, wolves, the mechanical wolf 机械狼, seer, witch, hunter, idiot, guard), then add each round: who died that night; the sheriff election, if there was one (who ran, who withdrew, how each player who stayed down voted, who won); and the day's statements, typed as people say them at the table (`3踩5，6跳预言家验2金水，1、2投5，5出局`) or tapped on a keypad that writes the same text. It shows each player's chance of being a wolf and of holding each role, the likeliest wolf teams, and how likely every two players are to be on the same side, and for any player, which statements moved them most. Your own seat and role count as certain, and so do your checks if you are the seer and the knife target if you are the witch. The game is kept in `localStorage` under `tableread.game`.
- `werewolf/engine.js` reads those statements and does the reasoning. Every deal of the board's cards is a possible world, each piece of evidence weighs each world by how likely it would be there, and the weights, with a short reason for each, are at the top of the file. The mechanical wolf is a third state beside good and wolf, since it and the wolves don't know each other. It enumerates the wolf teams, then which of each team is the mechanical wolf, and deals the good roles with a small dynamic programme, so a 12-player game takes a few milliseconds and the 18-player maximum about a third of a second. Like `golf/swing.js` it has no DOM, so node can run it.
- `terroir/index.html` is 风土 Terroir, the wine primer at `/terroir/`, in Chinese and English: how each style of wine is made, step by step, with the chemistry of fermentation and how long each style sits on its skins; 36 grapes with their structure, aromas and food; and a map of 59 regions that zooms into each one's villages and sub-regions, and in France and the United States on down to the official appellation boundaries, Burgundy's to every premier and grand cru. The map moves like any other: drag it, zoom with + and −, two fingers, or Ctrl (⌘ on a Mac) and the wheel. A scale bar in its lower right corner gives a round length, measured across the middle of the map, in every view but the world's. Close in, it lies on satellite imagery, Esri World Imagery as in Fall Line, with the appellations as tints and outlines over it; a button turns the imagery off. Over Napa it also shows each vineyard's outline and the name it carries, learned from Vinous's maps with permission, and a search finds where an owner or a vineyard has its blocks; see [Vinous's vineyards of Napa](#vinouss-vineyards-of-napa). The imagery's tiles are Web Mercator and the map is not, so the page draws each tile on a canvas between the flat map and the appellations, with the affine map its corners take into the view's projection, which from tile zoom 8 on is true to about a pixel. Everything it says is in `terroir/data.js`, each text a pair [Chinese, English], and the comment at the top of that file explains every field, so changing the content means editing that file only. The Wine tab on the homepage links to it with a card edged in the colours wine takes in the glass.
- `terroir/map/` holds the map, one file per view (the world, Europe, France and so on): land, lakes, rivers and borders as SVG paths, drawn from Natural Earth by `terroir/tools/build-map.mjs`. The page puts the regions on it itself, so most edits need no new map; see [Redrawing the wine map](#redrawing-the-wine-map). `terroir/map/appellations/` holds the appellation boundaries, one file per wine area, which the page fetches when the map is zoomed into that area, and `napa-vineyards.json`, Napa's vineyards one by one with its wineries, roads and streams; see [Redrawing the appellations](#redrawing-the-appellations). `terroir/map/vinous/vineyards.json` holds Napa's vineyards as Vinous maps them, which is not open data: see the `NOTICE.md` beside it.
- 杰神模拟器 Jieshen Simulator (`/jaysonsays/`) and 滚落线 Fall Line (`/fallline/`) live in their own repositories, [VictorZG33/jaysonsays](https://github.com/VictorZG33/jaysonsays) and [VictorZG33/fallline](https://github.com/VictorZG33/fallline). GitHub Pages serves each at that path because project sites inherit this site's custom domain; the homepage links to them from its Wine and Skiing tabs.
- `photography/index.html` is 显影 Developed, the photography gallery. The Photography tab on the homepage links to it with a card, in a darkroom safelight's amber, that shows a strip of its first photographs. `photography/tools/build.mjs` makes both, with the images in `photography/img`, from full-size masters and `photography/photos.json`; see [Adding photographs](#adding-photographs).
- `404.html` is what GitHub Pages serves for any missing path; its links are absolute for that reason.
- `og.png`, `wine-moon/og.png`, `split/og.png`, `golf/og.png`, `werewolf/og.png` and `terroir/og.png` are the 1200×630 preview images link previews show. They are screenshots of the pages, so retake them if the name, strip, Wine Moon, All Square, Swing Mirror, Table Read or Terroir colours change. `beer/og.png` sets seven of Original Gravity's glasses, pale to dark, under its name, each a screenshot of the page's own drawing, so retake it if the glasses or their colours change. The gallery's preview is its first photograph, which the build script fills in.
- The light/dark choice is stored in `localStorage` under `wentaoz.theme` and shared by every page; with nothing stored, pages follow the system setting.

## Adding photographs

The gallery shows each photograph at a fixed size for each of three window sizes, as Apple's product pages do: it fits in 800 × 480, 1200 × 720 or 1600 × 960 CSS pixels, picked by the window's width and height so the whole frame and its caption fit on screen. The script makes exactly those widths for screens at 1x, 1.5x and 2x, so on a laptop or a desktop monitor every pixel of the image lands on one pixel of the screen and the browser never resamples it. Phones and narrow windows get a fluid layout and the next size up. Each size is made straight from the master with a Lanczos filter, sharpened lightly at that size and compressed once: AVIF at quality 72, which keeps film grain, and JPEG at 90 for browsers without AVIF, both with full colour resolution (4:4:4) and in Display P3, with no other metadata, so no EXIF or GPS position.

1. Export a master of each photograph from Lightroom: Display P3, long edge 4,000 px or more (the largest size sent to any screen is 3,200 px wide), TIFF or JPEG at quality 95, output sharpening for Screen, Standard. Fill in Title, Caption and the location in Lightroom and they are copied in. Photographs pasted into a Claude chat arrive at 2,000 px on the long edge, already recompressed: enough for square and upright frames, which are never shown wider than 1,920 px, but short for landscape ones, which the largest windows on 2x screens then enlarge. The script names the missing sizes.
2. Put the masters in `photography/masters/`. Git ignores that folder, so they stay on your computer. The file name, lower-cased, becomes the photograph's id and its address in the gallery: `XPan 01.tif` is `/photography/#xpan-01`.
3. Once, in `photography/tools`, run `npm ci` (Node 20.9 or newer). Then run `node build.mjs`, or `node build.mjs ~/path/to/masters` for masters kept elsewhere.
4. Edit `photography/photos.json`: `title`, `alt` (what the photograph shows, for people who can't see it), `place`, `date`, `camera` and `film`. The list's order is the gallery's order, and the card on the homepage shows the first few, as many as fit in one strip. `width` and `height` are the master's size; the script keeps them. Run `node build.mjs` again: without new masters it only rewrites the two pages.
5. Commit `photography/` and `index.html`.

To take a photograph down, delete it from `photos.json` and run the script; its files go with it. A master newer than its files is made again, and `--force` remakes everything. Do that rarely: every remake adds a full set of files to the repository's history, and GitHub Pages wants a site under 1 GB. The script prints the size of `photography/img` after each run.

The window sizes are written twice, in `SIZES` in `build.mjs` and in the media queries in `photography/index.html`, so a change to one needs the same change in the other and `--force`.

## Redrawing the wine map

Each view of the map in 风土 Terroir has its own projection: Equal Earth for the world, so the wine belts between 30° and 50° are straight bands, and Lambert's azimuthal equal-area centred on the view everywhere else. The page projects each region's coordinates in `terroir/data.js` with the same parameters the map was drawn with, so a region's text, grapes, villages or position can change without redrawing anything, as long as it stays inside its view. Redraw the map after adding a region far from its view's frame, moving a region to another view, or adding a view (to `views` in `data.js` and to `VIEWS` in `build-map.mjs`):

1. Once, in `terroir/tools`, run `npm ci` (Node 20.9 or newer).
2. Run `node build-map.mjs`. The first run downloads the Natural Earth layers it needs (version 5.1.2, public domain, about 40 MB) into `terroir/tools/.cache`, which git ignores. It prints each view's size; all thirteen come to about 775 KB, and a visitor loads only the views they open.

A view keeps full detail only around its own regions, where the map zooms in, and draws everything else coarsely. Only the land borders that every major country's maps agree on are drawn, so disputed borders are left out. The villages and sub-regions (`spots`) were placed with OpenStreetMap's geocoder; place new ones the same way.

## Redrawing the appellations

The coloured boundaries on Terroir's zoomed-in maps of France and the United States come from two open datasets: INAO's [Délimitation parcellaire des AOC viticoles](https://www.data.gouv.fr/datasets/delimitation-parcellaire-des-aoc-viticoles-de-linao), the production area of every French wine appellation drawn parcel by parcel (Licence Ouverte; Champagne is not in it, so Champagne keeps its dots), and the [UC Davis AVA Project](https://github.com/UCDavisLibrary/ava)'s boundaries of the American Viticultural Areas (CC0). `terroir/tools/build-appellations.mjs` sorts each appellation into a wine area of the map and a tier: regional, sub-regional, village, premier cru, grand cru. Where appellations of one tier overlap, each piece goes to the smallest, so Chambertin comes out without Clos de Bèze, which may be sold as Chambertin. The boundaries are drawn in the coordinates of the view they sit on, and each tier is simplified for the zoom it is seen at: to a few metres for the climats, while the large regional appellations are closed into zones across the roads and woods between INAO's parcels. The areas shown are the delimited ones, measured before that closing.

1. Once, in `terroir/tools`, run `npm ci`.
2. Run `node --max-old-space-size=8192 build-appellations.mjs`. The first run downloads both datasets (about 270 MB and 43 MB) into `terroir/tools/.cache`, which git ignores. It takes about ten minutes and prints each area's size, and every appellation that came out empty because others cover all of it, such as a premier cru name that only groups climats of its own. All fifteen areas come to about 2.4 MB, and a visitor fetches only the ones they zoom into. `AREAS=burgundy,chablis node build-appellations.mjs` rebuilds just those.

Run it again after redrawing a view the areas sit on (France, California, Oregon & Washington, New York & Ontario), or to take in a new release of either dataset, after deleting its folder in `.cache`. Which appellations are drawn, and at what tier, is set by the tables at the top of the script (`GRANDS_CRUS`, `BORDEAUX`, `LOIRE` and the rest), and how finely each tier is drawn by `SHAPES`. The Chinese names on the map are `appellationsZh` in `terroir/data.js`; an appellation without one, a climat above all, keeps its own name.

Closer in, Napa has a map of its own: its 4,600 vineyards drawn one by one over the AVAs, which are outlined on top, with 430 wineries and the roads, the Napa River, its creeks and lakes. The page loads it closer than 160 metres per pixel, as soon as Napa is picked. The vineyards, roads and water are OpenStreetMap's, through the [Overture Maps](https://overturemaps.org) release on Amazon S3. The wineries come first from Wikidata, then from Overture's places, which put a winery at its owner's office as readily as at its estate. So a place is kept only when nothing contradicts it:
- it lies within 200 m of a vineyard;
- it lies outside Napa's airport industrial parks;
- Wikidata doesn't have the same name;
- Overture doesn't put that name in two places a kilometre apart;
- it doesn't come from BrightQuery, a business registry, which gives where a company is registered;
- its name isn't an office's, a restaurant's or a town tasting room's.

In the script, `fix` places Robert Mondavi, for which neither source gives the estate, and `former` drops Inglenook's names from before 2011. To rebuild it:

1. Once, in `terroir/tools`, run `python3 -m venv .venv && .venv/bin/pip install duckdb==1.4.1`.
2. Run `.venv/bin/python fetch-vineyards.py`, which reads only the parts of the Overture release that cover Napa, about a minute, and asks Wikidata for its wineries, into `terroir/tools/.cache/overture`.
3. Run `AREAS=napa-vineyards node build-appellations.mjs` (the full build draws it too).

`terroir/map/appellations/napa-vineyards.json` is a database derived from OpenStreetMap, © OpenStreetMap contributors, and is available under the [Open Database License](https://opendatacommons.org/licenses/odbl/1-0/); its wineries are from Wikidata (CC0) and the Overture Maps Foundation's places ([CDLA Permissive 2.0](https://cdla.dev/permissive-2-0/)). To draw another area this way, add it to `AREAS` in `fetch-vineyards.py` and to `DETAIL` in `build-appellations.mjs`.

## Vinous's vineyards of Napa

Over Napa, Terroir's map shows the vineyards as Vinous maps them: each parcel's outline and the name it carries, from the eight maps of Vinous's *The Vineyards of Napa Valley*, by Antonio Galloni with Alessandro Masnaghetti. The eight are Howell Mountain, St. Helena & Conn Valley, Rutherford, Pritchard Hill, Oakville, Yountville, Stags Leap and Coombsville, © 2016–2023 Vinous Media LLC. **They are used with Vinous's written permission, for personal study and exchange only; no commercial use of any kind is allowed.** `terroir/map/vinous/vineyards.json` is not open data and nothing in this repository licenses it; `terroir/map/vinous/NOTICE.md` says so in full, and the page credits Vinous with the same terms wherever the vineyards show.

Nothing of the maps' look is kept. The page draws the parcels itself:
- as a wash, half clear, each parcel parted from the next by a hairline of the paper, or of white over the satellite imagery; on the flat map the AVAs' tints all but fade beneath them;
- one colour an owner (the name before ' - ', as Vinous writes 'Owner - Vineyard'), so that neighbouring owners differ and each colour covers about as much of the valley as the others. The eight colours are muted, like the land's own (claret, rosé, terracotta, ochre, olive, sage, slate and plum), with a set each for the light map, the dark one and the imagery, every pair checked apart for normal and colour-blind vision;
- names where the parcels lie. An owner's parcels within 100 m of each other are one place, named for the owner once its parcels cover, on screen, six times the name's width in pixels, which for the largest is with most of the valley in view; closer in, each of its vineyards takes its whole name once it has room. A name sits on a parcel Vinous set it on, the one nearest the middle of the place, and the larger places are placed first. The tooltip gives each parcel's name with its AVA, its area and the source.

Parcels Vinous draws as vineyards but leaves unnamed are only outlined, dashed. Where the maps reach, the open data's vineyards and their names give way. A button on the map, *Vinous vineyards*, hides them; the page keeps the choice in `localStorage` under `terroir.vinous`. There are about 3,800 parcels under about 840 names, a tenth of them unnamed, 400 kB.

Near Napa a search field sits beside the way back, at the top left of the map. It matches what is typed anywhere in a name, ignoring case, accents, stops and apostrophes, so `bosche` finds Bosché and `stags leap` both Stag's Leap Wine Cellars and Stags' Leap Winery. The suggestions are:
- the owners whose name matches, each with the vineyards Vinous names for it, its places and its land;
- then the vineyards whose own name matches, as `to kalon` finds each owner's block of To Kalon;
- when those are more than one owner's, a row for all of them, first unless an owner has just the name typed.

Choosing one, by click or with the arrow keys and Enter, lights its parcels and fades the rest. It marks each place with a ring and the vineyard's name, whatever its size, names nothing else, and moves the map to show it all in the part the search and the legend leave clear. Under the field, how many places and how much land; clicking that brings the map back to them. Escape or × clears the search.

How they were found:

1. `terroir/tools/georef-vinous.py` finds where each map lies. The maps are north up, and their SVG units are points of paper at about the scale printed on them, so a map's own AVA boundary (for Pritchard Hill, the shore of Lake Hennessey) laid on the edge of what it draws gives a first fit. OpenStreetMap's main roads, matched to Vinous's in each 1.5 km of the map and combined by RANSAC, then fix it to a few metres: a median miss of 2 to 5 m. Coombsville's roads are drawn too faintly for that, so it keeps its boundary fit, to a median of about 6 m. The result, a scale, rotation and shift for each map, is in `terroir/tools/vinous-georef.json`; `georef-vinous.py --check` fits each map on the roads again from there and says how far it would move, which today is 1 to 21 m at the corners.
2. `terroir/tools/build-vinous.py` reads each SVG shape by shape. The parcels are the filled shapes that are not paper, text, buildings, water, terrain or lines. A fill counts as terrain if one of its shapes covers 60 ha, or if they cover 20 ha and wind like the bands between contours.
3. Vinous names a vineyard in a box laid over it, or beside it with a thin line to a dot on it. Each box's text is drawn alone from its glyphs, line by line, and read by Tesseract; Coombsville's text is live. A second reader, RapidOCR, agreed on all but 17 of the 900 or so names in outline, and those, with names whose accents the glyphs show but Tesseract dropped, were checked by eye. The 20 it misread are corrected in `terroir/tools/vinous-names.json`.
4. The parcel under a box, or at the end of its line, is the name's; a box with nothing under it takes the parcel just beside it. Vinous draws an owner's parcels alike, so parcels that look the same within 80 m of it, and of those, are the name's too. Looking the same is having the same fill, or, since Coombsville gives every parcel a pattern of its own, about the same colour as drawn over the same fill beneath.
5. Where maps overlap, a parcel is kept from the map that shows there: the map of its own AVA first, by the UC Davis boundaries, then Pritchard Hill over its own ground, else the map whose AVA is nearest. Parcels in a map's margin, as in Pritchard Hill's enlarged insets, are left out.

To rebuild, with the SVGs, which are not in this repository, in a folder of their own:

1. Once, in `terroir/tools`, run `python3 -m venv .venv && .venv/bin/pip install numpy scipy scikit-image pillow shapely svgelements`, install Tesseract (`apt install tesseract-ocr`, or `brew install tesseract`), and install Playwright's Chromium for Node (`npm i -g playwright && npx playwright install chromium`). The AVA boundaries and OpenStreetMap's roads come from the caches `build-appellations.mjs` and `fetch-vineyards.py` fill; see [Redrawing the appellations](#redrawing-the-appellations).
2. Run `VINOUS_DIR=<that folder> .venv/bin/python build-vinous.py`, about five minutes; it rewrites `terroir/map/vinous/vineyards.json`. Naming maps (`build-vinous.py rutherford`) reads only those and writes, to `terroir/tools/.cache/vinous`, what was read in each box (`<id>.json`) and a picture of the parcels found, each name's in a colour (`<id>.png`), for checking; add a misread name to `vinous-names.json` by its map and box number.
3. Only for a new edition of a map: update its entry in `vinous-georef.json` (file, title, year, printed scale), run `VINOUS_DIR=<that folder> .venv/bin/python georef-vinous.py <its id>`, check the fit it prints, and rebuild. If the vineyards' extent changes, update `VIN_BOX` in `terroir/index.html` from the `box` in `vineyards.json`.

## Shared ledgers in All Square

A ledger stays in the browser until someone shares it. Sharing saves it to the sync server, and the link carries only its id (`#l=<id>`). Every page that has the ledger open asks the server for changes every 5 seconds, and two people editing at once don't overwrite each other: a save made from an outdated copy is refused, and the page replays its changes on the newer one. The server is the Cloudflare Worker in `workers/split`. It keeps each ledger in its own Durable Object and deletes a ledger nobody has changed for a year.

Until `API` near the top of the script in `split/index.html` holds the server's address, share links are snapshots that carry the whole ledger after `#d=`, so later changes don't reach them. The page also falls back to snapshots when the server can't be reached, as from mainland China, where `workers.dev` addresses are blocked.

To set the server up once:

1. Make a free Cloudflare account and open **Workers & Pages** once; it asks you to pick a `workers.dev` subdomain.
2. Under **My Profile → API Tokens**, create a token from the **Edit Cloudflare Workers** template, and copy your account ID from the **Workers & Pages** overview.
3. Store them as the repository secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` (Settings → Secrets and variables → Actions).
4. Actions → Split sync server → Run workflow. The run's summary shows the server's address, `https://split-sync.<subdomain>.workers.dev`.
5. Put that address in `API` in `split/index.html` and push.

From then on `.github/workflows/split-sync.yml` redeploys the server whenever `workers/split` changes on `main`. The free plan allows 100,000 requests a day, and a page with a shared ledger open makes about 720 an hour.

To try it locally, run `npx wrangler dev --var DEV_ORIGINS:http://localhost:8000` in `workers/split`, serve the repo with `python3 -m http.server 8000`, and point `API` at `http://localhost:8787` without committing that.

## Visitor counting and the visitor map

The homepage, Wine Moon, Terroir, Original Gravity, All Square, Swing Mirror, Table Read and the photography gallery load [GoatCounter](https://www.goatcounter.com) (site code `wentaoz`), which counts visits without cookies. To leave your own visits out, open `https://wentaoz.com/#toggle-goatcounter` once in each browser you use.

The Visitors section on the homepage stays hidden until there is something to show. It reads two sources:

- **The total**, from GoatCounter's public counter (`https://wentaoz.goatcounter.com/counter/TOTAL.json`). This needs *Allow adding visitor counts on your website* switched on in the GoatCounter site settings.
- **The map and the country list**, from `visitors.json` in this repo. `.github/workflows/visitors.yml` rebuilds the file every day at 06:17 UTC by running `.github/scripts/visitors.mjs`, and commits it when the counts change. The script reads the GoatCounter API with a key stored as the repository secret `GOATCOUNTER_TOKEN`; that key needs only the permission to read statistics. Countries are placed at the centres in `.github/scripts/country-centres.json`.

To run it by hand: Actions → Visitor map → Run workflow.
- `CNAME` tells GitHub Pages which custom domain to serve (don't delete it).
- `.nojekyll` turns off Jekyll processing so the files are served as-is.
